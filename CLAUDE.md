# MyHotkey — рабочие заметки

Переназначение клавиш для Windows. Цель — заменить AutoHotkey: то же самое, но
настраивается мышкой и стартует мгновенно. Это продукт, а не личный скрипт.

## Правила работы

**Коммить каждый законченный кусок.** Не ждать просьбы и не сваливать сессию в
один коммит. Один коммит — одна связная единица: модуль, исправленная ошибка,
работающая функция. Перед коммитом собрать и прогнать тесты; дерево, которое не
собирается, не коммитить.

**Не писать C через heredoc в Bash.** Он съедает уровень экранирования обратных
слешей: `L'\\'` превращается в `L'\'`, и файл перестаёт компилироваться. Писать
исходники напрямую инструментом записи файлов.

**Держать сборку без предупреждений.** Сейчас `-Wall -Wextra` даёт ноль.

**UI — только стандартные контроли WPF, без своих ControlTemplate и неявных
стилей.** Первая версия перекрашивала всё вручную и получила чёрный текст на
синей кнопке: неявный стиль TextBlock уровня приложения просачивается внутрь
шаблонов контролов и перебивает Foreground, заданный кнопкой. Ориентир по
компоновке — BetterTouchTool: список слева, настройка выбранного справа,
изменения применяются сразу, без модальных окон и кнопки «Сохранить».

## Сборка

```
build-all.bat      # движок + окно настроек + тесты
build.bat gcc      # только движок, принудительно MinGW
build.bat msvc     # только движок, принудительно MSVC
test\run.bat       # тесты
install.bat        # установка с автозапуском, просит права администратора
```

Тулчейн на этой машине: MinGW-w64 в `C:\Users\ils\tools\mingw64`, его надо
добавить в PATH. Windows SDK не установлен, поэтому MSVC движок собрать не может —
попытки поставить SDK через winget и через установщик VS обе провалились.

UI собирается MSBuild из VS2019 Build Tools. Reference assemblies есть только
версии 4.8.1, поэтому проект нацелен на неё, хотя рантайм на машине 4.8. Это
проверено и работает: .NET Framework 4.x един, обновляется на месте, и атрибут
целевой версии при загрузке не проверяется.

## Проверка вживую

Логику сопоставления удобно проверять правилом с действием `launch`, которое
создаёт файл-маркер: результат детерминирован, в отличие от наблюдения за
раскладкой, которая зависит от того, какое окно в фокусе.

Синтетический ввод шлётся через `keybd_event`; для правых модификаторов и стрелок
обязателен флаг расширенной клавиши, иначе придёт не тот код.

Окно снимается через `PrintWindow` с флагом `PW_RENDERFULLCONTENT`, а не
`CopyFromScreen`: вывести чужое окно на передний план из фонового процесса
Windows не даёт, и снимок захватит то, что лежит поверх.

Тесты:

```
gcc -O1 -Wall -Wextra -DUNICODE -D_UNICODE -D_WIN32_WINNT=0x0601 \
    -o build/test_keys.exe test/test_keys.c engine/keys.c -luser32
build/test_keys.exe
```

## Архитектура

Два процесса, и это главное решение проекта:

```
myhotkey-engine.exe   ~100 КБ, чистый Win32 на C, без рантайма
                      на автозагрузке, в трее; хук + правила + config.json
myhotkey-ui.exe       WPF на .NET Framework 4.8 (рантайм уже внутри Windows)
                      запускается из трея, на автозагрузку не влияет
```

Отсюда мгновенный старт: на автозагрузке только голый нативный бинарник.
Общение — через `config.json` и именованный канал `\\.\pipe\myhotkey`.

## Что важно не сломать

**Колбэк хука обязан быть быстрым.** Если он выйдет за `LowLevelHooksTimeout`
(250 мс), Windows молча выбросит хук, и всё перестанет работать без единого
сообщения об ошибке. Поэтому в [engine/hook.c](engine/hook.c) только поиск по
таблице, а вся работа постится сообщением в окно движка и выполняется там.

**Своя инжекция помечается подписью.** `dwExtraInfo == MH_SIGNATURE` в
[engine/action.c](engine/action.c); хук такие события пропускает, иначе получится
бесконечный цикл. Чужую инжекцию пропускать нельзя — ремап ремапа осмыслен.

**Колбэк хука выполняется в том же потоке**, что и цикл сообщений, — его
диспетчеризует наш же `PeekMessage`. Поэтому подмена набора правил гонки не
создаёт, блокировки не нужны.

**Звук ругани играется со своего потока и не даёт устройству заснуть.**
Windows усыпляет звуковую конечную точку примерно через полминуты тишины, и
первый звук после этого выходит с задержкой: замерено на этой машине —
`waveOutOpen` вхолодную 820 мс, а на уже открытом устройстве после 45 с
простоя первый буфер всё равно опаздывает на 640 мс. Поэтому
[engine/sound.c](engine/sound.c) держит устройство открытым и каждые 20 секунд
подливает 120 мс тишины: с такой подкормкой задержка — единицы миллисекунд.
Подкормка идёт, только пока в конфиге вообще есть кому ругаться. И это второй
повод для отдельного потока: `PlaySound` вызывался с потока движка, на котором
Windows исполняет колбэк хука, а секунда там — четыре бюджета
`LowLevelHooksTimeout`.

**Занятый мьютекс — не доказательство, что движок жив.** Установщик гасит
старый движок и тут же запускает новый, а труп держит хендлы ещё примерно
полсекунды после возврата `taskkill`. Поверить мьютексу здесь — значит выйти с
кодом 0 и оставить машину вообще без движка, причём тихая установка
отрапортует успех. Проверено: `schtasks /end` + сразу `/run` воспроизводит это
стабильно. Поэтому [engine/main.c](engine/main.c) сначала спрашивает у
владельца окна, жив ли он через секунду, и только потом уступает.

**Движок под задачей работает elevated, и обычные процессы до него не
достучатся.** UIPI молча роняет `PostMessage` из процесса со средней
целостностью в окно привилегированного — второй запуск exe «перечитай конфиг»
возвращал ошибку 5 и не делал ничего. Лечится `ChangeWindowMessageFilterEx` на
одно это сообщение; прав это не добавляет, потому что тот же пользователь и так
правит `config.json`, который движок перечитывает сам. Канал к UI такой
проблемы не имеет — там уже есть явный дескриптор в [engine/ipc.c](engine/ipc.c).

**Имена не должны сталкиваться с Win32.** `Chord` занят GDI, `MOD_ALT` и соседи —
`winuser.h`. Свои типы и константы с префиксом `Mh`/`MH_`.
