# Ревью MyHotkey

Дата ревью: 2026-08-30.

## Итог

Архитектурное разделение на маленький нативный движок и запускаемый по
требованию WPF-редактор удачное. Hook callback делает только сопоставление и
публикует сообщения, конфигурация заменяется атомарно, собственный
синтетический ввод помечается подписью, а правила по умолчанию выключены.

Главная проблема текущей архитектуры — граница привилегий: движок запускается
с `highest`, но полностью управляется данными и командами из обычного процесса
того же пользователя. Кроме неё найдены ошибки жизненного цикла hook,
конфигурации и UI.

## Найденные проблемы

### 1. Critical: обычный процесс может использовать движок для повышения привилегий

Связанные места:

- `installer/myhotkey.iss:70` — задача запускает движок с `/rl highest`.
- `engine/config.c:25` — конфигурация хранится в `%APPDATA%` и доступна
  процессам среднего integrity level.
- `engine/ipc.c:26` — pipe разрешает подключение процессам с SID пользователя;
  SID не отличает medium integrity от elevated-процесса того же пользователя.
- `engine/hook.c:105` — hook намеренно принимает синтетический ввод других
  программ.
- `engine/action.c:132` — действие `launch` вызывает `ShellExecuteW` из
  elevated-процесса.

Из этого следует локальный сценарий повышения привилегий для пользователя,
входящего в Administrators:

1. Обычный процесс записывает правило `launch` в пользовательский
   `config.json`.
2. Он вызывает `reload` через pipe либо ждёт file watcher.
3. Он отправляет триггер через `SendInput`.
4. Движок запускает заданную команду с высоким integrity level без нового UAC.

Действия `text` и `combo` также превращают движок в доверенного посредника,
способного вводить данные в elevated-окна по указанию любого обычного процесса
пользователя.

Рекомендуемое решение: не исполнять пользовательские `launch`, `text` и
`combo` в high-integrity процессе. Предпочтительный вариант для такого
продукта — подписанный `uiAccess=true` executable, установленный в защищённый
каталог Program Files. Альтернатива — разнести перехват и исполнение по разным
процессам и запускать действия через medium-integrity broker, оставив
привилегированному компоненту минимальный закрытый протокол.

Документация Microsoft:

- https://learn.microsoft.com/en-us/windows/win32/sbscs/application-manifests
- https://learn.microsoft.com/en-us/windows/security/application-security/application-control/user-account-control/settings-and-configuration

### 2. High: тяжёлая работа выполняется на том же потоке, который обслуживает hook

Связанные места:

- `engine/main.c:182` — `mh_action_run` вызывается из window procedure.
- `engine/action.c:120` — `ACT_TEXT` выполняет отдельный `SendInput` для каждого
  UTF-16 code unit; размер конфигурации допускает очень длинный текст.
- `engine/ipc.c:104` — запись в pipe способна блокировать поток на 1000 мс.

Low-level hook вызывается в контексте установившего его потока через сообщение.
Быстрый callback сам по себе недостаточен: пока этот же поток печатает длинный
текст, ждёт pipe или запускает программу, он не может принять очередной вызов
hook. Windows ограничивает `LowLevelHooksTimeout` одной секундой и может удалить
hook без уведомления.

Рекомендуемое решение: выделить hook и его message loop в отдельный поток. В
нём оставить только обновление состояния, сопоставление и неблокирующую
постановку неизменяемого задания; действия и IPC выполнять worker-потоком.

Документация Microsoft:

- https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc

### 3. High: queued action может обратиться уже к другому набору правил

Связанные места:

- `engine/hook.c:142` и `engine/hook.c:154` — в сообщение передаётся только
  индекс правила.
- `engine/main.c:101` — reload заменяет весь `g_rules`.
- `engine/main.c:182` — обработчик позднее разрешает индекс через текущий
  `g_rules`.

Если reload обработан между публикацией `MH_WM_RUN_ACTION` и выполнением
сообщения, старый индекс применяется к новому массиву. Это может выполнить
другое действие, включая другой `launch`. Очистка `g_swallowed` проблему уже
опубликованных сообщений не решает.

Рекомендуемое решение: присваивать набору правил generation ID и передавать его
вместе с индексом, отбрасывая устаревшие задания. Ещё надёжнее — публиковать
неизменяемый снимок действия, время жизни которого не зависит от reload.

### 4. Medium: несколько редакторов и внешние изменения теряют данные

Связанные места:

- `engine/main.c:126` — каждое открытие настроек запускает новый UI-процесс.
- `ui/MainWindow.xaml.cs:35` — у UI нет singleton/activation механизма.
- `ui/Config.cs:236` — редактор сохраняет полный снимок списка без проверки,
  что файл не менялся после загрузки.
- `ui/Config.cs:289` — сохранение использует `File.Replace`.
- `engine/main.c:123` — watcher подписан только на
  `FILE_NOTIFY_CHANGE_LAST_WRITE`.

Два открытых окна перезаписывают изменения друг друга по правилу last writer
wins. То же происходит с ручным редактированием. Кроме того, внешний редактор,
который сохраняет через временный файл и rename, может не вызвать watcher,
поскольку изменение имени не отслеживается. UI маскирует это собственным
`reload`, но внешние редакторы его не отправляют.

Рекомендуемое решение:

1. Сделать UI singleton и активировать уже открытое окно.
2. Перед сохранением сравнивать timestamp/hash загруженной версии и предлагать
   reload/merge при конфликте.
3. Добавить `FILE_NOTIFY_CHANGE_FILE_NAME` и повторно открывать watcher при
   ошибках.
4. В `read_all` рассмотреть `FILE_SHARE_DELETE`, чтобы не конфликтовать с
   атомарной заменой.

### 5. Medium: ошибочный reload течёт по памяти

Связанные места:

- `engine/config.c:158` — `id`, `name` и `whenApp` текущего правила уже могут
  быть выделены.
- `engine/config.c:172` — `parse_action` после этого может завершиться ошибкой.
- `engine/config.c:174` — `out->count` увеличивается только при полном успехе.
- `engine/config.c:188` — `mh_config_free` освобождает только элементы с
  индексом меньше `count`.

При ошибке action поля текущего правила не освобождаются. Повторные уведомления
для повреждённого или специально большого файла дают неограниченную утечку.

Рекомендуемое решение: иметь отдельную функцию очистки одного `Rule` и вызывать
её для текущего элемента перед `goto bad`, либо учитывать элемент в `count` с
момента появления первой принадлежащей ему аллокации.

### 6. Low: capture timeout не сбрасывает состояние UI

Связанные места:

- `engine/main.c:230` — движок отправляет `capture timeout`.
- `ui/Engine.cs:68` — клиент молча игнорирует строку.
- `ui/MainWindow.xaml.cs:293` — локальный `_recording` остаётся активным.

Через минуту движок возвращает клавиатуру, но окно продолжает показывать режим
записи и ждать событие, которое уже не придёт.

Рекомендуемое решение: добавить в `Engine` событие `CaptureTimedOut`, обработать
его через Dispatcher и вызвать UI-эквивалент `StopRecording` без повторной
отправки команды. Аналогично сбрасывать запись при `Disconnected`.

### 7. Low: повтор одного modifier group создаёт недопустимое значение стороны

Связанные места:

- `engine/keys.c:228` — стороны модификаторов объединяются через OR.
- `engine/keys.c:331` — matcher обрабатывает только `ANY`, `LEFT` и `RIGHT`.

Например, `LCtrl+RCtrl+S` даёт значение стороны `3`. Matcher не распознаёт его и
может принять сочетание даже без Ctrl. UI такое сочетание не создаёт, но формат
конфигурации объявлен редактируемым вручную.

Рекомендуемое решение: отклонять повтор modifier group в `mh_parse_chord` и
добавить отрицательные тесты для одинаковых и конфликтующих повторов.

## Покрытие тестами

Проверено во время ревью:

- engine и icon resource собираются MinGW GCC с `-Wall -Wextra` без
  предупреждений;
- WPF UI собирается MSBuild;
- `test/test_keys.c`: 44 проверки, все прошли.

Текущий автоматический набор покрывает только разбор, форматирование и matching
сочетаний. Он не проверяет:

- успешный и ошибочный разбор полной конфигурации;
- утечки/повторные reload;
- порядок queued action и reload;
- фрагментацию и разрыв named pipe;
- capture timeout/disconnect;
- одновременное сохранение из двух UI;
- integrity level и доверие между UI, конфигурацией и elevated-движком.

Для исправлений выше нужны как минимум модульные тесты config/parser и
интеграционные тесты IPC/reload. Риск привилегий требует отдельной проверки под
medium- и high-integrity процессами Windows.

## Рекомендуемый порядок работ

1. Сначала устранить Critical-границу привилегий и зафиксировать выбранную
   модель безопасности в документации/manifest/installer.
2. Вынести hook на выделенный поток и ввести безопасный immutable job или
   generation ID.
3. Исправить утечку config и добавить parser/config tests.
4. Сделать UI singleton и защититься от конфликтов сохранения.
5. Обработать timeout/disconnect и расширить интеграционные тесты.

После каждого логического исправления собирать обе части, запускать тесты и
делать отдельный коммит, как требует `CLAUDE.md`.
